Barometer — Adaptations pour une intégration fluide dans synapsun.com

Croisement du pipeline Barometer (scraper TaiyangNews → Google Sheets → dashboards GitHub Pages) avec le fonctionnement réel du portail synapsun/portal (routes, entité Barometer, conventions Symfony/Stimulus, mode de livraison « code + specs »).

Diagnostic en une phrase

Le portail a déjà la page, la route SEO, l'admin, le rôle et le canal leads ; le pipeline Barometer a déjà les données fraîches et l'automatisation. Il manque entre les deux : un contrat de données stable, un front conforme aux conventions du portail, et la suppression des dépendances tierces côté client (CSP, RGPD, fiabilité).

2. PHASE 0 Adaptations immédiates — dans Barometer, sans toucher au portail

Quatre chantiers entièrement réalisables dans le repo Barometer, qui gardent leur valeur quel que soit l'arbitrage hébergement.

2.1 Contrat de données JSON versionné — la pièce maîtresse

Le portail ne doit jamais parser le CSV gviz Google (format non contractuel, quota, dépendance frontale à Google). Ajouter au run hebdo un export publié sur GitHub Pages, ex. data/barometer.json :

{
  "schema_version": 1,
  "generated_at": "2026-07-17T08:12:00Z",
  "last_week": "W28-2026",
  "fx": { "usd_eur": 0.86, "cny_eur": 0.12, "xag_usd_oz": 38.2, "fixed_at": "2026-07-17" },
  "market_comment": { "fr": null, "en": null },
  "categories": [ { "name": "Module", "products": [
    { "name": "TOPCon Module", "unit": "USD/W", "show_in_barometer": true,
      "series": [ { "week": "W27-2026", "value": 0.087 } ],
      "wow_change_pct": -1.1, "trend_4w": "down" } ] } ]
}
  • Nouveau script export_json.py + step dans pv_price_weekly.yml.
  • FX et prix de l'argent figés à la génération → permet de supprimer les 4 appels d'APIs tierces du navigateur (§3.3).
  • schema_version obligatoire ; champ market_comment FR/EN prévu dès maintenant (vide) pour le Lot 1 de la roadmap v2.

2.2 Génération automatique image + PDF au format admin du portail

Le « court terme zéro dev portail » : rendu headless (Playwright dans le runner Actions) → PNG ≤ 2 Mo + PDF ≤ 4 Mo (contraintes exactes de l'entité Barometer) + meta title/description proposées, au dernier run du mois. L'humain ROLE_BAROMETER ne fait plus que valider l'upload EasyAdmin.

2.3 Correction des canonicals / SEO

Anomalie constatée

Les canonicals et hreflang du dashboard pointent vers des pages qui n'existent pas sur synapsun.com — les signaux SEO émis depuis GitHub Pages tombent sur des 404.

  • Option simple (recommandée) : aligner sur les routes réelles https://synapsun.com/barometre · https://synapsun.com/barometer.
  • Option ambitieuse : spec de renommage de route côté prestataire (URLs longues descriptives + redirections 301) — seulement si la valeur SEO du slug long est jugée décisive.

2.4 Basculer le dashboard GitHub Pages sur le JSON

Le dashboard consomme son propre barometer.json (CSV gviz en fallback). Il devient le client de référence du contrat de données — il le valide chaque semaine — puis servira de préversion une fois la page portail en place.

6. Décisions à trancher (gouvernance)

  1. Arbitrage hébergement (question bloquante déjà posée dans synapsun_com) : page interactive sur le portail (recommandé) vs GitHub Pages avec lien. La Phase 1 en dépend ; la Phase 0 non.
  2. Pull vs push pour les données (§3.2) — recommandation : (a) cron pull.
  3. Iframes Zoho Analytics : remplacement natif (recommandé) vs maintien transitoire lazy-load.
  4. Slug SEO : conserver /barometre (simple) vs renommage en URL longue + 301 (spec prestataire supplémentaire).
